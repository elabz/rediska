# search-indexing Specification

## Purpose
Rediska maintains an Elasticsearch index over local content (messages, lead posts, profiles, conversations) and exposes a single search API that blends BM25 full-text relevance with kNN dense-vector similarity. Embeddings are generated by an external llama.cpp-compatible endpoint. This capability covers the global `/search` API and page, the indexing tasks, and the embedding tasks — not the in-conversation or inbox search UIs (see `conversation-search` and `inbox-search`).

## Requirements

### Requirement: Search API supports hybrid, text, and vector modes

The core API SHALL expose `POST /search` accepting a query and a `mode` of `hybrid`, `text`, or `vector`. `text` mode SHALL rank by BM25 only; `vector` mode SHALL rank by kNN dense-vector similarity of the query embedding; `hybrid` mode SHALL blend both signals, weighting BM25 at 0.3.

#### Scenario: Hybrid search blends both signals

- **WHEN** a client calls `POST /search` with `mode: "hybrid"` and a non-empty query
- **THEN** the query is embedded via the configured embeddings endpoint and a kNN search runs against the `embedding` dense-vector field
- **AND** a BM25 match runs against the `text` field
- **AND** results are ranked by the blended score with BM25 contributing weight 0.3

#### Scenario: Text mode works without an embeddings endpoint

- **WHEN** a client calls `POST /search` with `mode: "text"`
- **THEN** results are ranked by BM25 relevance only
- **AND** no embedding call is made

### Requirement: Search results are filterable by document type and visibility

The search API SHALL accept a `doc_types` filter restricting results to any subset of `message`, `lead_post`, `profile`, and `conversation`. By default, documents whose remote visibility marks them deleted/removed SHALL be excluded; an explicit include-deleted flag SHALL allow callers to opt in to locally-hidden content.

A caller-supplied `exclude_visibility` list SHALL be applied to the executed query as a negative constraint: every document whose `remote_visibility` matches any listed value SHALL be absent from the results. A filter that the API accepts SHALL NOT be silently discarded — if a supplied filter cannot be applied, the request SHALL fail with an error rather than return a wider result set than the caller asked for.

Documents whose `remote_visibility` field is absent SHALL NOT be excluded by an `exclude_visibility` list, since absence does not indicate a matching visibility state.

#### Scenario: Filtering to one document type

- **WHEN** a client searches with `doc_types: ["lead_post"]`
- **THEN** every hit in the response has `doc_type` equal to `lead_post`

#### Scenario: Remote-deleted content excluded by default

- **WHEN** a client searches without an include-deleted flag
- **THEN** documents marked remote-deleted/removed or locally deleted are absent from the results

#### Scenario: Explicit visibility exclusion is applied

- **WHEN** a client searches with `exclude_visibility: ["removed", "deleted_by_author"]`
- **THEN** the query sent to the search engine carries a negative clause for those values
- **AND** no returned hit has a `remote_visibility` of `removed` or `deleted_by_author`

#### Scenario: Documents without a visibility field survive exclusion

- **WHEN** a client searches with a non-empty `exclude_visibility` list
- **AND** a matching document has no `remote_visibility` field
- **THEN** that document is still returned

#### Scenario: An unapplicable filter fails the request

- **WHEN** a client supplies a filter the search layer cannot apply
- **THEN** the request fails with an error
- **AND** no result set is returned that is wider than the filter requested

### Requirement: Indexed documents use stable composite identifiers

Every indexed document SHALL be identified in Elasticsearch as `doc_type:entity_id`, so re-indexing the same entity upserts in place rather than duplicating.

#### Scenario: Re-indexing an updated message

- **WHEN** `index.upsert_content` runs twice for the same message
- **THEN** the index contains exactly one document with id `message:<id>`, reflecting the latest content

### Requirement: Indexing runs as idempotent background tasks

Content SHALL be indexed by Celery tasks on the `index` queue: `index.upsert_content` and `index.delete_content` for single documents, plus `index.bulk_index_all_messages` (batched, default 500) and `index.bulk_index_conversation` for backfill. Ingest flows SHALL enqueue indexing so newly synced content becomes searchable without manual action.

#### Scenario: New message becomes searchable

- **WHEN** a sync ingests a new message
- **THEN** an `index.upsert_content` task is enqueued and, once processed, the message is returned by `/search`

### Requirement: Embeddings are generated via the configured llama.cpp endpoint

Dense-vector embeddings SHALL be produced by Celery tasks on the `embed` queue — `embed.generate` (raw text), `embed.generate_batch`, and `embed.generate_for_entity` (fetches the entity's text from the DB) — calling the endpoint configured by `EMBEDDINGS_URL`/`EMBEDDINGS_MODEL`/`EMBEDDINGS_API_KEY`, and stored on the document's `embedding` field.

#### Scenario: Embedding an entity by reference

- **WHEN** `embed.generate_for_entity` runs for an indexed entity
- **THEN** the entity's text is loaded from the database, embedded via the embeddings endpoint, and written to the corresponding ES document

### Requirement: Global search page deep-links results

The web app SHALL provide a `/search` page that calls `POST /api/core/search` and renders result cards per doc type, each deep-linking to the owning surface (conversations to `/inbox/<id>`, lead posts to `/leads/<id>`, profiles to the account profile page).

#### Scenario: Clicking a message hit

- **WHEN** the user clicks a search result of type `message`
- **THEN** the browser navigates to the conversation containing that message in `/inbox`
